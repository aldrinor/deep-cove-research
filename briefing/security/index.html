The Core has no internet path. BC controls every crossing.

Deep Cove runs Kit on hardware BC owns, inside a BC facility. Patient records never leave the facility.1 The only things that go out to the internet are cleaned search words and requests for the public pages those searches return, with no patient identifiers.

Most AI services ask a hospital to trust a policy.

The vendor promises not to look at patient data, not to keep it and not to train on it.

A policy can drift. A missing cable cannot.

Deep Cove runs the model on a server with no internet path.

The model can act only by placing fixed-form orders, which separate machines check, log and fulfil.

BC gets a system that lists and logs every crossing, and BC can check each one on site.

The keys, the logs and the update decision are held in BC.

Five crossings. Nothing else gets in or out.

The Core is the server that runs Kit.

It sits inside a shielded enclosure in a BC facility, and it has no cable, route or radio to the internet.

How a gate works. Each gate is built from one-way optical links: the sending end has a light source, the receiving end has only a light sensor, so nothing can travel back along that fibre. A question and its answer travel on two separate fibres (the Monitoring Gate has one, outbound only), and each fibre ends in a single-purpose checker on its own hardware, so no network session ever crosses.

Patient records never leave the facility. The Records Librarian reads the health authority's record systems over its own network and hands the Core only the fields a question needs, under pseudonyms.

Names return on the clinician's screen, never inside the Core.

One line reaches the internet, and it carries searches only. The Web Librarian's fetcher holds Deep Cove's single outbound line.

Before a search leaves, two independent checks refuse any search that contains a name, a health or chart number, a date, an address, a postal code or a phone number (doses and lab values pass only with their units), and the Librarian rebuilds the query from approved medical terms.

The fetcher then requests the public pages the search returns.

It never holds patient data, accepts no inbound connection and cannot open one to the Librarian, which pulls the pages and parses them on its own hardware.

A site can remove even that line. The Sealed Library option replaces live search with a curated medical library kept on site and refreshed through the Delivery Bay.

In that configuration the Web Librarian has no outbound line.

Patient records and search words stay in the facility.

Core hardening, delivered with every Deep Cove system:

  • no default route, no DNS resolver and no wireless hardware (radio modules absent at intake, recorded on the intake checklist);
  • management controllers (BMC) cabled only to the on-site out-of-band switch;
  • Secure Boot with BC-owned keys, and measured boot into TPM 2.0 (NIST SP 800-193);
  • a read-only, integrity-checked root file system;
  • model weights on read-only volumes, checked against a pinned hash at every load;
  • full-disk encryption with keys sealed to the TPM and escrowed in the hardware security module;
  • USB disabled in firmware and blocked, except the keyed, alarmed update reader;
  • host firewalls that deny everything except the gate interfaces (NIST SC-7(5)).

Library modes. Connected Library (standard): the fetcher is the only machine with an internet line, and only cleaned, rebuilt search words and requests for the public pages they return leave.

We measured Kit's published scores with live web search on Kit's current hosted service.

The on-site score re-run at acceptance measures them again through the installed Web Librarian.

Sealed Library (per-site option): a curated library mirrored on the Web Librarian, from open public sources such as the Health Canada Drug Product Database extract, the PubMed baseline and BC Guidelines, plus any references BC licenses, refreshed through the Delivery Bay.

The Web Librarian then has no outbound line.

A site that chooses the Sealed Library has its scores re-run in that mode at acceptance.

The site's privacy officer sets the mode at commissioning.

Power. The Core runs on hospital power, delivered with an online double-conversion UPS sized at 1.25 times the design load and 10 to 15 minutes of runtime to bridge to the hospital generator.

An Emergency Power Off switch sits at the enclosure (NIST PE-10, PE-11).

Physical. Two-person entry with badge and PIN.

Cameras on the enclosure door and console.

Alarmed door contacts and chassis-intrusion switches.

Serial-numbered tamper-evident seals checked at every entry; phone lockers at the door; filtered power entry.

The enclosure is radio-shielded.

Shielding stops radio emissions and hidden wireless.

It does not stop low-frequency magnetic or power-line channels (published as ODINI and PowerHammer), which is why the phone-free rule, filtered power and the double-conversion UPS are part of the specification.

Five guarantees. BC checks each one itself.

A guarantee is worth what its verification is worth.

Each of the five below names the mechanism that enforces it and the check BC's own team runs.

YesNo internet path to the Core

The Core has no cable, route, DNS or radio to the internet.

Its only connections are the four gates, each built from one-way optical links that end on separate machines.

How BC checks it. At acceptance, BC's testers try to reach the internet from the Core and record the failure.

The intake record lists every port and confirms that no radio hardware is present.

YesOrders only, checked twice

Deep Cove does not trust the model.

It holds no credentials, has no write path and cannot send a web address or a database query.

Its search words are short, checked twice and rebuilt from approved terms, and it can only place an order from a fixed menu, which a separate machine checks against a schema and business rules before acting.

How BC checks it. The order schema is in the Architecture Brief, and BC's penetration testers send malformed and free-text orders at the gates.

The gate log shows each one dropped whole.

YesNo training on patient records

Patient records are never used to train any model.

The Deep Cove system ships with no training system: no training jobs, no training data store and a read-only model, hash-checked at every load.

The agreement forbids any secondary use.

How BC checks it. BC compares the hash of the loaded weights with the hash in the signed release record, and inspects the software bill of materials for every installed component.

YesNo remote administrator access

Deep Cove Intelligence has no remote path into the system: no vendor portal, no remote-access account and no management port reachable from outside.

Administration happens at the on-site console, and emergency credentials are held by named BC custodians.

How BC checks it. BC's network team compares the firewall rules with the zone diagram, and the system records every console session and announces it to the hospital's security operations.

YesA log of every crossing, held by BC

Kit writes every question, answer, order, gate decision and administrative action to a hash-chained journal in which each record carries the hash of the one before.

Deep Cove systems ship with daily signed checkpoints and write-once export, so a changed record shows.

How BC checks it. An auditor role reads the journal without reading chats, recomputes the chain and samples the outbound search log.

The privacy officer receives a daily sample and a weekly report.

Order schema, outbound guard and sanitization

Pattern. Each gate follows the UK NCSC “Safely Importing Data” pattern (transform, protocol break, verify) and NCSC Cross Domain Approach and Architecture (v1.0, 21 April 2026), and maps to NIST SP 800-53 Rev 5 AC-4 with enhancements (7) one-way flow, (25) data sanitization, (26) audit filtering actions, (27) redundant and independent filtering and (31) failed content transfer prevention.

Order fields. Order id (UUIDv4); an opaque 128-bit session reference that is not a user or patient id.

A timestamp that must fall within ±30 s of the gate clock; the order type.

Search terms of at most 128 characters and 12 tokens from a fixed character set; language (en, fr); 1 to 10 results; for a web read, a result reference issued by the librarian in the same session; for a records lookup, a session pseudonym, a record kind from a fixed list, fields from a fixed per-kind list, and a window of 1 to 3,650 days.

The Core signs every order with a key held in its TPM.

Response fields. Up to 10 items, each with a librarian-issued reference, a plain-text title of at most 300 characters, the source name, the publication date, and plain UTF-8 text of at most 24,000 characters with control, zero-width and bidirectional characters stripped.

The librarian signs every response with its key.

Outbound guard, six layers (Web Gate):

  1. a check inside the Core that refuses any term matching the session's masked identifiers or pseudonyms;

  2. an independent guard in the Web Librarian, on a separate code base: detectors for BC Personal Health Number shapes, other health-card and record-number shapes, full dates, Canadian postal codes, phone numbers, email and street addresses, and person names.

    A medical and general vocabulary allow-list; numbers allowed only with units.

    Entropy and shape checks against encoded strings;

  3. the outbound query rebuilt from canonical vocabulary terms, never forwarded byte for byte;
  4. per-session and per-site rate caps;
  5. one shared outbound address, with no cookies, accounts or user identifiers sent to any search service;
  6. every outbound query and every block logged, with a daily sample to the privacy officer.

Inbound sanitization. Two independent sanitizers on different code bases rebuild every page and document as plain text in a fixed envelope (content disarm and reconstruction).

The gate drops whole, and logs, a message that fails any check.

Records Librarian. It acts with the requesting clinician's rights, never a broad service identity: the Front Door signs a session assertion that the Core can relay but not forge, and the librarian checks it on every lookup (NIST AC-3, AC-6, SP 800-207).

It is read-only.

The Front Door detects and masks identifiers typed into chat.

The Records Librarian replaces record identifiers with session pseudonyms by field.

Volume. A maximal research run reads about 950 pages.

At an assumed 30 KB of text per page that is about 28.5 MB, which a 1 Gbit/s one-way link carries in about 0.23 s. Gate checks run on small messages.

The acceptance test measures the delay per crossing.

Every update is built by Deep Cove, checked and safety-tested by BC on separate machines, carried in on sealed media and installed by two people, and the previous version stays installed.

  1. Signed build. Deep Cove builds every release reproducibly, with signed provenance, a software bill of materials and model weights pinned by hash.

  2. BC's test station. On a BC-owned station, offline, BC verifies the signatures, rebuilds the code from source and compares hashes, scans with three or more malware engines, and runs Kit's clinical safety suite on a test system.

    Any failure blocks the release.

  3. Two sign-offs. The security officer and the clinical safety officer each sign before the release moves on.

  4. Sealed media, two people. Code arrives on write-once discs and model weights on a hardware write-protected, encrypted drive.

    Two people install it on camera, and the update reader checks the signatures again.

  5. Side-by-side install. The release installs beside the running version and becomes the live version only after automatic health and clinical checks pass.

BC can decline any update. The Sealed Library's content arrives by the same path.

One-step rollback

If any automatic check fails, the system stays on the previous version with no human step.

A manual return to the last verified version is one console action by two people.

A timed drill at acceptance measures rollback time.

Emergency Safety Lock

Three levels, each one action away. Pause Kit: the Front Door stops new questions entering the Core.

Sever Gates: keyed physical switches cut the chat, records and web gates. The one-way Monitoring Gate stays up.

Power Off: the enclosure's Emergency Power Off.

Break-glass access

Emergency administrator access needs several named people, in person, at the on-site console.

Every use alerts the hospital's security operations, goes on record in full, and ends with new credentials.

  • Build: hermetic, reproducible builds (NIST SP 800-218 SSDF) with SLSA Build L3 provenance; SBOM in CycloneDX or SPDX.

  • Media: write-once optical discs for code.

    Hardware write-protected, encrypted drives for weights, mounted through a write-blocker, so the system can never write onto the drive.

  • Slots: operating system and application images in A/B slots, each integrity-protected.

    Model weights as versioned read-only volumes with the current, candidate and last-known-good versions on disk.

    An offline golden image on encrypted media is kept in a safe for full rebuild (NIST CP-9, CP-10).

  • Test system by tier: Deep Cove Hospital and larger systems include a dedicated test server.

    Deep Cove Clinic tests each update on its own server in a maintenance window, or on an optional stand-alone test server.

  • Break-glass custody: the hardware security module generates emergency credentials and splits them between five named custodians.

    It takes any three of them.

    The shares sit in sealed, tamper-evident envelopes in separate safes.

    BC rotates credentials within 24 h of any use and reviews each use within 72 h (NIST AC-3(2), AU-9, AU-10, IR-4).

Questions a security reviewer asks.

Which AI model runs inside?

Deep Cove does not trust the model, whichever it is. The model runs on BC-owned hardware with no network, no credentials and no write path.

It can only place schema-checked orders through the Gates, and its weights are hash-checked at every load.

The buyer receives the model's identity and its evaluations under NDA in due diligence.

What happens if the internet line goes down?

Kit keeps answering from the Core. Only live web lookups pause.

Kit Ask, Kit Think Medical and records lookups continue.

A site with the Sealed Library has no internet line to lose.

Who holds the keys?

BC does. BC's hardware security modules generate the data keys and disk recovery keys, and BC holds them.

Five named BC custodians each hold a share of the break-glass credentials, in sealed envelopes in separate safes, and it takes any three of them.

Deep Cove Intelligence holds only the key that signs its software releases, and BC's test station checks that signature before BC installs anything.

Can Deep Cove Intelligence see our data or switch the system off remotely?

No. There is no remote path into the system.

Deep Cove engineers work on site, at the console, with BC staff present, and the system records every session.

How is it accepted?

On site, through seven acceptance gates: capacity, speed, scores, clinical safety, security (an independent penetration test), recovery (a timed rollback drill and an emergency lock drill) and privacy.

BC sets the pass marks and signs every gate.

Kit is clinical decision-support software for licensed professionals. The clinician decides. It shows its sources, and the clinician reviews them.

Image and document reading is non-diagnostic.

Diagnostic imaging follows the Health Canada medical-device pathway.
