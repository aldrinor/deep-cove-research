What crosses the wall, and what never does

The Core is the server that runs Kit. It has no cable, route or radio to the internet.

  1. 1Questions in, answers outChat Gate
  2. 2Record requests out, records inRecords Gate
  3. 3Cleaned search words out, public pages inWeb Gate

Never leaves the facility

  • Patient Records
  • Prompts with Identifiers
  • Model Weights or Logs
  • Vendor Telemetry

Never enters

  • Remote Administrator Sessions

Each gate is built from one-way optical links. Nothing travels back, and no network session ever crosses.

One line reaches the internet, for cleaned search words only. The Sealed Library removes even that line.

Expert DetailRecords, Outbound Checks, Zones and Hardening
  • Records. The Records Librarian hands the Core only the fields a question needs, under pseudonyms. Names are restored on the clinician's screen.
  • Outbound checks. Two independent checks refuse any search with a name, a health or chart number, a date or an address. The Librarian then rebuilds the query from approved medical terms.
  • Sealed Library. A curated medical library kept on site and refreshed through the Delivery Bay.
  • Zones. Deep Cove follows the Canadian Centre for Cyber Security network-zone model (ITSP.80.022 v2.0). Every flow between zones passes one zone interface point.
  • The Core (Highly Restricted) talks to the Chat, Records and Web Gates, and to the one-way Monitoring Gate out. Nothing else.
  • The fetcher (Public Access) has one outbound-only HTTPS line to an allow-list of sources. It is re-imaged every 24 h from a read-only signed image.
  • Keys and Audit Log (Management) sit on the enclosure's own hardware, with two FIPS 140-3 hardware security modules. There is no remote administration path.
  • Core hardening. No default route, no DNS resolver and no wireless hardware. Secure Boot with BC-owned keys. Model weights are checked against a pinned hash at every load. USB is blocked, except the keyed update reader.
  • Power. The online double-conversion UPS is sized at 1.25 times the design load. It gives 10 to 15 minutes of runtime to bridge to the hospital generator.
  • Physical. Two-person entry, cameras, tamper-evident seals and phone lockers. The enclosure is radio-shielded.

Five guarantees, and how BC checks each one

Each guarantee names its mechanism and the check BC's own team runs.

  1. No Internet Path to the Core

    The Core has no cable, route, DNS or radio to the internet. Its only connections are the four gates.

    How BC checks itBC's testers try to reach the internet from the Core and record the failure.

  2. Orders Only, Checked Twice

    The model holds no credentials and has no write path. It can only place an order from a fixed menu, which a separate machine checks.

    How BC checks itBC's penetration testers send malformed orders at the gates. The gate log shows each one dropped whole.

  3. No Training on Patient Records

    The system is delivered with no training system and a read-only model. The agreement forbids any secondary use.

    How BC checks itBC compares the hash of the loaded weights with the hash in the signed release record.

  4. No Remote Administrator Access

    Deep Cove Intelligence has no remote path into the system. Administration happens at the on-site console.

    How BC checks itBC's network team compares the firewall rules with the zone diagram. Every console session is recorded.

  5. A Log of Every Crossing, Held by BC

    Every question, answer, order and administrative action is written to a hash-chained journal. A changed record shows.

    How BC checks itAn auditor role recomputes the chain. The privacy officer receives a daily sample.

The Gates and the Two Librarians

The model never opens a connection. It writes an order. A gate carries it one way to a librarian, which checks it and sends plain text back.

Four gates, seven one-way links per site. A message that fails a check is dropped whole and logged.

GateWhat crossesHow it is checked
Chat GateQuestions in; answers outOnly fixed-format chat turns reach the Core.
Records GateRecord orders out; records in, under pseudonymsEvery order is checked against the signed-in clinician's own access rights.
Web GateOrders out; plain text inOrders that carry an identifier are refused. Pages return as plain text, so no script reaches the Core.

Injected instructions have nowhere to go. Text from a web page is treated as quoted source material. If it did sway the model, the only possible action would be another checked order.

Expert DetailOrder Schema, Outbound Guard and Sanitization
  • The order menu. Web Search, Web Read, Library Lookup and Records Lookup.
  • Pattern. Each gate follows the UK NCSC “Safely Importing Data” pattern and maps to NIST SP 800-53 Rev 5 AC-4.
  • Orders. An order carries an id, a timestamp, its type and a session reference. The reference is not a user or patient id. Search terms are at most 128 characters and 12 tokens. Every order is signed with a key held in the Core's TPM.
  • Responses. Up to 10 items of plain UTF-8 text, at most 24,000 characters each, signed with the librarian's key.
  • Outbound guard, six layers. A check inside the Core. An independent guard in the Web Librarian, on a separate code base. The query rebuilt from canonical terms. Rate caps. One shared outbound address, with no cookies or accounts. Every query and block logged.
  • Inbound. Two independent sanitizers on different code bases rebuild every page as plain text.
  • Volume. A maximal research run reads about 950 pages, about 28.5 MB. A 1 Gbit/s one-way link carries that in about 0.23 s.

Updates through the Delivery Bay

Nothing reaches the Core over a network. BC tests every update, two people install it, and the previous version stays installed.

  1. Signed Build

    Deep Cove builds every release reproducibly and signs it, with model weights pinned by hash.

  2. BC's Test Station

    Offline, BC verifies the signatures, rebuilds from source and scans for malware. It then runs Kit's clinical safety suite.

  3. Two Sign-Offs

    The security officer and the clinical safety officer each sign.

  4. Sealed Media, Two People

    Code arrives on write-once discs. Two people install it on camera.

  5. Side-by-Side Install

    The release is promoted only after automatic health and clinical checks pass.

BC can decline any update.

Expert DetailRollback, Safety Lock, Supply Chain and Custody
  • One-step rollback. If any automatic check fails, the system stays on the previous version. A manual return is one console action by two people.
  • Emergency safety lock. Three levels, each one action away: pause Kit, sever the Gates, power off.
  • Break-glass access. Emergency access needs several named people, in person. Every use alerts the hospital's security operations.
  • Build. Reproducible builds (NIST SP 800-218 SSDF) with SLSA Build L3 provenance and an SBOM; Ed25519 signatures.
  • Test station. Signature check against keys pinned at commissioning; three or more malware engines; Kit's safety regression.
  • Media. Write-once optical discs for code; hardware write-protected, encrypted drives for weights. Each item is used once and sanitized under NIST SP 800-88 Rev. 2.
  • Break-glass custody. Credentials are split between five named custodians, any three of whom are needed. They are rotated within 24 h of any use.
  • Test system by tier. Hospital and larger systems include a dedicated test server. Clinic tests each update on its own server in a maintenance window.

Every Network Session Encrypted, and Fast

Every connection to Kit uses TLS 1.3, with key exchange built to resist future quantum computers. Kit is never published to the internet.

Who Gets In

  • Device. Only hospital-managed devices holding a certificate can open a connection.
  • Person. Staff sign in with the health authority's own single sign-on and multi-factor authentication.
  • Session. Sessions can be revoked at once. The inactivity lock is set by BC.

Encrypted in transit and at rest, with keys BC holds. Post-quantum protection costs about 0.2 milliseconds, once per connection.

  • Storage. Disks are encrypted with AES-256. Stored chats and documents are encrypted again under keys wrapped in BC's hardware security module.
  • Measured. The hybrid key exchange took 2.37 ms against 2.18 ms for the classical one.
  • Dropped connections. If Wi-Fi drops mid-answer, the answer resumes where it stopped.

Questions a security reviewer asks

Which AI model runs inside?

Deep Cove does not trust the model, whichever it is. It runs with no network, no credentials and no write path. Its identity and its evaluations are provided to the buyer under NDA in due diligence.

What happens if the internet line goes down?

Kit keeps answering from the Core. Only live web lookups pause.

Who holds the keys?

BC does. Data keys are generated in BC's hardware security modules. Deep Cove Intelligence holds only the key that signs its software releases.

Can Deep Cove Intelligence see our data or switch the system off remotely?

No. There is no remote path into the system. Deep Cove engineers work on site, with BC staff present, and every session is recorded.

How is it accepted?

On site, through seven acceptance gates: capacity, speed, scores, clinical safety, security, recovery and privacy. BC sets the pass marks and signs every gate.

Kit is clinical decision-support software for licensed professionals. It shows its sources, and the clinician decides.

Image and document reading is non-diagnostic. Diagnostic imaging follows the Health Canada medical-device pathway.
