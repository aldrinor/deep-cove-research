Abstract

Most AI services ask a hospital to trust a policy: the vendor promises not to look at patient data, not to keep it and not to train on it. A policy can drift; a missing cable cannot. Deep Cove runs the model on a server with no internet path and lets it act only by placing fixed-form orders, which separate machines check, log and fulfil. BC gets a system in which every crossing is listed, logged and checkable on site, with the keys, the logs and the update decision held in BC.

1What crosses the wall, and what never does

The Core is the server that runs Kit. It sits inside a shielded enclosure in a BC facility, and it has no cable, route or radio to the internet.

How a gate works. Each gate is built from one-way optical links: the sending end has a light source, the receiving end has only a light sensor, so nothing can travel back along that fibre. A question and its answer travel on two separate fibres (the Monitoring Gate has one, outbound only), and each fibre ends in a single-purpose checker on its own hardware, so no network session ever crosses.

Patient records never leave the facility. The Records Librarian reads the health authority's record systems over its own network and hands the Core only the fields a question needs, under pseudonyms. Names are restored on the clinician's screen, never inside the Core.

One line reaches the internet, and it carries searches only. The Web Librarian's fetcher holds Deep Cove's single outbound line. Before a search leaves, two independent checks refuse any search that contains a name, a health or chart number, a date, an address, a postal code or a phone number (doses and lab values pass only with their units), and the Librarian rebuilds the query from approved medical terms. The fetcher then requests the public pages the search returns. It never holds patient data, accepts no inbound connection and cannot open one to the Librarian, which pulls the pages and parses them on its own hardware.

A site can remove even that line. The Sealed Library option replaces live search with a curated medical library kept on site and refreshed through the Delivery Bay. In that configuration the Web Librarian has no outbound line; patient records and search words stay in the facility.

Core hardening, delivered with every Deep Cove system:

  • no default route, no DNS resolver and no wireless hardware (radio modules absent at intake, recorded on the intake checklist);
  • management controllers (BMC) cabled only to the on-site out-of-band switch;
  • Secure Boot with BC-owned keys, and measured boot into TPM 2.0 (NIST SP 800-193);
  • a read-only, integrity-checked root file system;
  • model weights on read-only volumes, checked against a pinned hash at every load;
  • full-disk encryption with keys sealed to the TPM and escrowed in the hardware security module;
  • USB disabled in firmware and blocked, except the keyed, alarmed update reader;
  • host firewalls that deny everything except the gate interfaces (NIST SC-7(5)).

Library modes. Connected Library (standard): the fetcher is the only machine with an internet line, and only cleaned, rebuilt search words and requests for the public pages they return leave. Kit's published scores were measured with live web search on Kit's current hosted service; the on-site score re-run at acceptance measures them again through the installed Web Librarian. Sealed Library (per-site option): a curated library mirrored on the Web Librarian, from open public sources such as the Health Canada Drug Product Database extract, the PubMed baseline and BC Guidelines, plus any references BC licenses, refreshed through the Delivery Bay; the Web Librarian then has no outbound line. A site that chooses the Sealed Library has its scores re-run in that mode at acceptance. The site's privacy officer sets the mode at commissioning.

Power. The Core runs on hospital power, delivered with an online double-conversion UPS sized at 1.25 times the design load and 10 to 15 minutes of runtime to bridge to the hospital generator. An Emergency Power Off switch sits at the enclosure (NIST PE-10, PE-11).

Physical. Two-person entry with badge and PIN; cameras on the enclosure door and console; alarmed door contacts and chassis-intrusion switches; serial-numbered tamper-evident seals checked at every entry; phone lockers at the door; filtered power entry. The enclosure is radio-shielded. Shielding stops radio emissions and hidden wireless; it does not stop low-frequency magnetic or power-line channels (published as ODINI and PowerHammer), which is why the phone-free rule, filtered power and the double-conversion UPS are part of the specification.

2Five guarantees, and how BC checks each one

A guarantee is worth what its verification is worth. Each of the five below names the mechanism that enforces it and the check BC's own team runs.

  1. No Internet Path to the Core

    The Core has no cable, route, DNS or radio to the internet. Its only connections are the four gates, each built from one-way optical links that end on separate machines.

    How BC checks itAt acceptance, BC's testers try to reach the internet from the Core and record the failure; the intake record lists every port and confirms that no radio hardware is present.

  2. Orders Only, Checked Twice

    Deep Cove does not trust the model. It holds no credentials, has no write path and cannot send a web address or a database query; its search words are short, checked twice and rebuilt from approved terms, and it can only place an order from a fixed menu, which a separate machine checks against a schema and business rules before acting.

    How BC checks itThe order schema is in the Architecture Brief, and BC's penetration testers send malformed and free-text orders at the gates; the gate log shows each one dropped whole.

  3. No Training on Patient Records

    Patient records are never used to train any model. The Deep Cove system is delivered with no training system: no training jobs, no training data store and a read-only model, hash-checked at every load. The agreement forbids any secondary use.

    How BC checks itBC compares the hash of the loaded weights with the hash in the signed release record, and inspects the software bill of materials for every installed component.

  4. No Remote Administrator Access

    Deep Cove Intelligence has no remote path into the system: no vendor portal, no remote-access account and no management port reachable from outside. Administration happens at the on-site console, and emergency credentials are held by named BC custodians.

    How BC checks itBC's network team compares the firewall rules with the zone diagram, and every console session is recorded and announced to the hospital's security operations.

  5. A Log of Every Crossing, Held by BC

    Every question, answer, order, gate decision and administrative action is written to a hash-chained journal in which each record carries the hash of the one before. Deep Cove systems are delivered with daily signed checkpoints and write-once export, so a changed record shows.

    How BC checks itAn auditor role reads the journal without reading chats, recomputes the chain and samples the outbound search log; the privacy officer receives a daily sample and a weekly report.

The model can only ask for a result the librarian already gave it. A web read names a result from the librarian's own list, never a free address, which closes the “hide data in a web address” path.

Injected instructions have nowhere to go. Text from a web page or a document is treated as quoted source material. If it did sway the model, the model's only possible action would be another order: still checked, still stripped of identifiers, still rate-limited and logged. The containment does not depend on the model resisting.

The gates are not the bottleneck. A one-gigabit link moves the text of a full research run in a fraction of a second.

Expert DetailOrder Schema, Outbound Guard and Sanitization

Pattern. Each gate follows the UK NCSC “Safely Importing Data” pattern (transform, protocol break, verify) and NCSC Cross Domain Approach and Architecture (v1.0, 21 April 2026), and maps to NIST SP 800-53 Rev 5 AC-4 with enhancements (7) one-way flow, (25) data sanitization, (26) audit filtering actions, (27) redundant and independent filtering and (31) failed content transfer prevention.

Order fields. Order id (UUIDv4); an opaque 128-bit session reference that is not a user or patient id; a timestamp that must fall within ±30 s of the gate clock; the order type; search terms of at most 128 characters and 12 tokens from a fixed character set; language (en, fr); 1 to 10 results; for a web read, a result reference issued by the librarian in the same session; for a records lookup, a session pseudonym, a record kind from a fixed list, fields from a fixed per-kind list, and a window of 1 to 3,650 days. Every order is signed with a key held in the Core's TPM.

Response fields. Up to 10 items, each with a librarian-issued reference, a plain-text title of at most 300 characters, the source name, the publication date, and plain UTF-8 text of at most 24,000 characters with control, zero-width and bidirectional characters stripped. Every response is signed with the librarian's key.

Outbound guard, six layers (Web Gate):

  1. a check inside the Core that refuses any term matching the session's masked identifiers or pseudonyms;
  2. an independent guard in the Web Librarian, on a separate code base: detectors for BC Personal Health Number shapes, other health-card and record-number shapes, full dates, Canadian postal codes, phone numbers, email and street addresses, and person names; a medical and general vocabulary allow-list; numbers allowed only with units; entropy and shape checks against encoded strings;
  3. the outbound query rebuilt from canonical vocabulary terms, never forwarded byte for byte;
  4. per-session and per-site rate caps;
  5. one shared outbound address, with no cookies, accounts or user identifiers sent to any search service;
  6. every outbound query and every block logged, with a daily sample to the privacy officer.

Inbound sanitization. Two independent sanitizers on different code bases rebuild every page and document as plain text in a fixed envelope (content disarm and reconstruction). A message that fails any check is dropped whole and logged.

Records Librarian. It acts with the requesting clinician's rights, never a broad service identity: the Front Door signs a session assertion that the Core can relay but not forge, and the librarian checks it on every lookup (NIST AC-3, AC-6, SP 800-207). It is read-only. Identifiers typed into chat are detected and masked at the Front Door; record identifiers are replaced with session pseudonyms by field.

Volume. A maximal research run reads about 950 pages; at an assumed 30 KB of text per page that is about 28.5 MB, which a 1 Gbit/s one-way link carries in about 0.23 s. Gate checks run on small messages; the acceptance test measures the delay per crossing.

4Updates through the Delivery Bay

Nothing reaches the Core over a network. Every update is built by Deep Cove, checked and safety-tested by BC on separate machines, carried in on sealed media and installed by two people, and the previous version stays installed.

  1. Signed Build

    Deep Cove builds every release reproducibly, with signed provenance, a software bill of materials and model weights pinned by hash.

  2. BC's Test Station

    On a BC-owned station, offline, BC verifies the signatures, rebuilds the code from source and compares hashes, scans with three or more malware engines, and runs Kit's clinical safety suite on a test system. Any failure blocks the release.

  3. Two Sign-Offs

    The security officer and the clinical safety officer each sign before the release moves on.

  4. Sealed Media, Two People

    Code arrives on write-once discs and model weights on a hardware write-protected, encrypted drive. Two people install it on camera, and the update reader checks the signatures again.

  5. Side-by-Side Install

    The release installs beside the running version and is promoted only after automatic health and clinical checks pass.

BC can decline any update. The Sealed Library's content arrives by the same path.

Rollback

One-Step Rollback

If any automatic check fails, the system stays on the previous version with no human step. A manual return to the last verified version is one console action by two people. Rollback time is measured in a timed drill at acceptance.

Safety Lock

Emergency Safety Lock

Three levels, each one action away. Pause Kit: the Front Door stops new questions entering the Core. Sever Gates: keyed physical switches cut the chat, records and web gates; the one-way Monitoring Gate stays up. Power Off: the enclosure's Emergency Power Off.

Break-Glass

Break-Glass Access

Emergency administrator access needs several named people, in person, at the on-site console. Every use alerts the hospital's security operations, is recorded in full, and is followed by new credentials.

Expert DetailSupply Chain, Media and Custody
  • Build: hermetic, reproducible builds (NIST SP 800-218 SSDF) with SLSA Build L3 provenance; SBOM in CycloneDX or SPDX; Ed25519 signatures, with an optional ML-DSA second signature (on the Cyber Centre's recommended list, ITSP.40.111 v5). NIST CM-14 signed components.
  • Test station: two BC-owned machines, an intake computer and a test system; signature check against keys pinned at commissioning; independent rebuild with byte-for-byte hash comparison; three or more malware engines on offline signatures (NIST SI-3) plus YARA rules; SBOM check against an offline vulnerability mirror; Kit's safety regression (dose rules, emergency-first ordering, crisis lines, red-team rows and a golden clinical question set). Dual sign-off per NIST CM-5(4).
  • Media: write-once optical discs for code; hardware write-protected, encrypted drives for weights, mounted through a write-blocker, so the system can never write onto the drive; every item logged, used once and sanitized under NIST SP 800-88 Rev. 2 (NIST MP-6, MP-7).
  • Install: two-person entry, seals checked and logged, recorded on camera; signatures re-verified by the update reader before staging (NIST SI-7, SI-7(15)).
  • Slots: operating system and application images in A/B slots, each integrity-protected; model weights as versioned read-only volumes with the current, candidate and last-known-good versions on disk. An offline golden image on encrypted media is kept in a safe for full rebuild (NIST CP-9, CP-10).
  • Test system by tier: Deep Cove Hospital and larger systems include a dedicated test server. Deep Cove Clinic tests each update on its own server in a maintenance window, or on an optional stand-alone test server.
  • Break-glass custody: emergency credentials are generated inside the hardware security module and split between five named custodians, any three of whom are needed; shares are sealed in tamper-evident envelopes in separate safes. Credentials are rotated within 24 h of any use, and each use is reviewed within 72 h (NIST AC-3(2), AU-9, AU-10, IR-4). At Clinic size, custodians may be health-authority staff outside the clinic.
  • Automatic pause: the Pause level can also trip on thresholds for gate schema rejections, outbound-guard blocks or unexpected port activity.

5Every Network Session Encrypted, and Fast

Every network connection to Kit is encrypted with TLS 1.3, including key exchange built to resist future quantum computers. Only managed hospital devices and signed-in staff get in, and Kit is never published to the internet.

Who Gets In

  • Device. Only hospital-managed devices holding a certificate from the health authority's own device service can open a connection; an unmanaged laptop on the same Wi-Fi never reaches the sign-in screen.
  • Person. Staff sign in with the health authority's own single sign-on and multi-factor authentication. Deep Cove is delivered with a check that refuses any sign-in token without a multi-factor claim.
  • Session. Sessions can be revoked at once, including “sign out everywhere”; an answer stream ends with its session; the inactivity lock is set by BC.

Clinicians away from the facility come in through the health authority's existing remote access, never through a public address.

Encrypted on every network session and at rest, with keys BC holds. TLS ends at the Front Door. Behind it, the gate fibres carry no network session at all: each message is signed by its sender and checked by its receiver, and the gate links stay inside the shielded enclosure; the one-way Monitoring link carries signed events with no patient text. Disks are encrypted with AES-256, and stored chats and documents are encrypted again under keys wrapped in BC's hardware security module.

Post-quantum protection costs about 0.2 milliseconds, once per connection. In our measurement, the hybrid key exchange took 2.37 ms against 2.18 ms for the classical one (median, loopback test).

If Wi-Fi drops mid-answer, the answer resumes where it stopped. The browser asks for the missing words by sequence number, and Kit replays them from its journal, with nothing lost or repeated.

Expert DetailProtocol Profile, Identity, Storage and Speed Sources

TLS profile (CCCS ITSP.40.062 v3): TLS 1.3 only; TLS_AES_256_GCM_SHA384, then TLS_AES_128_GCM_SHA256; 0-RTT early data off (RFC 8446: not forward secret, no replay guarantee between connections); HSTS; certificates from the health authority's own PKI, ECDSA P-256, with revocation served inside the network; HTTP/2, with answers streamed as server-sent events.

Hybrid post-quantum key exchange. X25519MLKEM768 first, with SecP256r1MLKEM768 offered as well. The hybrid is IETF Standards Track RFC 10024 (August 2026). ML-KEM is NIST FIPS 203 (13 August 2024) and is recommended for Protected B by CCCS ITSP.40.111 v5 (effective 29 May 2026). Current Chrome, Edge, Firefox and Apple version-26 operating systems offer it by default. Certificates stay ECDSA P-256 until browsers accept ML-DSA. This is post-quantum key exchange from day one, ahead of Canada's 2031 target for high-priority systems (ITSM.40.001, 23 June 2025). Measured cost: +0.19 ms median per handshake (2.37 vs 2.18 ms) and 1,088 extra bytes, once per connection. AES-256-GCM ran at 608 MB/s on one core of a 2016 server processor. Hospitals that inspect internal TLS exempt Kit's hostname, because mutual TLS fails by design through an inspecting proxy.

Identity. Mutual TLS with device certificates, selected automatically by browser policy, so clinicians see no prompt. Single sign-on: OpenID Connect with PKCE (matching RFC 9700); SAML 2.0 through an on-premises identity broker. Multi-factor enforced by the identity provider, preferably phishing-resistant (FIDO2 passkeys or smart cards, NIST SP 800-63B rev. 4); Kit's own MFA-claim check is a delivery item. Roles mapped from identity-provider groups, including an auditor role that reads the journal but not chats (delivery item). Suggested session defaults from NIST SP 800-63B rev. 4: 15 min inactivity and 12 h maximum on shared workstations; 1 h and 24 h on personal devices; BC sets the final values.

At rest. Full-disk AES-256-XTS on every server, keys sealed to TPM 2.0 measured-boot values, recovery keys held by BC; key-wrapping keys in a pair of FIPS 140-3 hardware security modules; application-layer AES-256-GCM for stored chats and documents under HSM-wrapped keys (delivery item); a hash-chained journal with daily signed checkpoints and write-once export (delivery items); retention set by BC per record type.

Kit Think Medical, hosted service: first visible line median 0.5 s (p90 1.4 s); finished answer medians 52.1 s for emergency questions, 90.7 s for dose questions and 109.2 s for symptom questions; n = 104 each. 9Questions a security reviewer asks

Which AI model runs inside?

Deep Cove does not trust the model, whichever it is. The model runs on BC-owned hardware with no network, no credentials and no write path; it can only place schema-checked orders through the Gates, and its weights are hash-checked at every load. The model's identity and its evaluations are provided to the buyer under NDA in due diligence.

What happens if the internet line goes down?

Kit keeps answering from the Core. Only live web lookups pause; Kit Ask, Kit Think Medical and records lookups continue. A site with the Sealed Library has no internet line to lose.

Who holds the keys?

BC does. Data keys and disk recovery keys are generated in BC's hardware security modules and held by BC; break-glass credentials are split between five named BC custodians, any three of whom are needed, in sealed envelopes in separate safes. Deep Cove Intelligence holds only the key that signs its software releases, and BC's test station checks that signature before anything is installed.

Can Deep Cove Intelligence see our data or switch the system off remotely?

No. There is no remote path into the system. Deep Cove engineers work on site, at the console, with BC staff present, and every session is recorded.

How is it accepted?

On site, through seven acceptance gates: capacity, speed, scores, clinical safety, security (an independent penetration test), recovery (a timed rollback drill and an emergency lock drill) and privacy. BC sets the pass marks and signs every gate.

Kit is clinical decision-support software for licensed professionals: it shows its sources, and the clinician reviews them and decides.

Image and document reading is non-diagnostic; diagnostic imaging follows the Health Canada medical-device pathway.
